# 観測地点を基準とする立入制約：経路部品の試作

> 履歴資料：この円制約は削除済み。以下の記述は当時のコミット `b54c06f` の実装を示す。

以下は経路部品の試作時点の記録。その後、実験用の制約付き訂正を探索実行器へ接続した。
当時の入口・検証範囲・制限は [CONSTRAINT_EXECUTION.md](CONSTRAINT_EXECUTION.md) を参照する。

日誌にある「訂正で変更する条件と維持する条件を区別する」という課題に向け、
まず過去の観測地点を中心とした円を、観測済み格子地図の経路から除外できるか試す。
中心は物体の位置ではなく、その色を観測した時の**ロボットの位置**を想定する。

`ObservedMap.routes(position, restricted)` は `(中心座標, 半径)` の組を受け取ると、
円から15 cmの余裕を含む範囲を経路候補から外す。元の観測済み空間や障害物データは書き換えない。
複数領域を扱い、制約の集合を減らして再計算できる。
現在地が領域内または余裕範囲内の場合は、近傍セルへの回復処理で領域を飛び越えずにエラーとする。
この半径は**ロボットの中心位置**の制約であり、機体全体を円外に保つ距離ではない。

単体テストでは、迂回経路が領域に入らないこと、領域内から始める操作の拒否、
解除後の経路復元、複数領域をイテレーターで渡しても途中で失わないことを確認した。
15 cmの余裕は格子の丸めや追従ずれを考慮した実装上の値であり、全状況の安全保証ではない。

Windowsでは71件のテストが成功し、物理テスト9件はスキップした。
WSLではMuJoCo物理テスト9件を含む71件が成功した（`outputs/restricted-map-regression-final.log`）。
その後、`traversable` 自体へイテレーターを渡す場合の消費漏れを修正したため、最終コードで4件の領域テストと
実MuJoCoによる制約なし探索・帰還を再実行し、5件とも成功した（`outputs/restricted-map-final-targeted.log`）。
制約を有効にした物理走行を検証したものではない。

## まだ接続していないこと

現在の探索実行器は `restricted` を渡していない。**自然言語による制約の追加・維持・解除も、
制約付きのMuJoCo歩行も、まだ実行できない。** 過去の実験結果は変更していない。
現時点では、連続的なロボットの位置監視や、制約適用時に帰還経路が残ることの確認もない。

実行器とは別に、制約の追加・維持・解除をLLMが解釈できるかを調べる
[言語試行](CONSTRAINT_LANGUAGE_PROBE.md)を用意した。この試行はロボットを動かさない。

再確認は今のところ過去の観測位置を目標にする。一方、道中の別の位置から新しい観測が得られる場合もある。
そのため「観測位置への接近禁止」と「再確認」の両立を一般に不可能と断定するのは誤り。
制約で既存の目標地点へ到達できないときは、現在の方法の限界を伝えて質問するか、
代替の観測位置を探す能力を別途実装する必要がある。

接続時には少なくとも次を満たす必要がある。

1. LLMの出力は、渡された観測IDに基づく限定された制約とし、座標や実行コードを直接受け取らない。
   訂正時に制約を暗黙に消さず、明示的な解除を記録する。
2. 適用前に現在地・帰還地点・既存タスクとの整合性を確認し、実行できない場合は適用せずに質問または停止する。
3. 制約付き経路を探索・再確認・帰還のすべてで使い、直接目標へ近づくショートカットでも領域を通らないことを確認する。
   歩行中も計測位置を確認し、逸脱時は停止する。物理追従の保証範囲は実験で別途測る。
4. 観測履歴・元の期限・帰還条件を保持した複数回の訂正で検証する。未使用配置の評価は、実装と条件を先に固定する。
