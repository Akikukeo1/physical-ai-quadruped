# 観測履歴を使う訂正の配置比較

方針変更後の既知のseed 305での成功から、同じ手続きで作る別配置への適用範囲を調べる。
実行前の仕様は [correction-evaluation.json](correction-evaluation.json)。
使用する配置・言い換え・順序・採点・中断規則を、最初の配置を調べる前にコミットする。

4配置 × 履歴あり／現在の観測のみの2条件、合計8試行。
後者でも地図、会話、タスク、帰還条件、実行器は同じで、LLMへ渡す過去の観測だけを減らす。
実行中の再確認タスクの参照先は残す。LLMが新たに参照先を選ぶ際の履歴の有無を比較するもので、
地図や観測履歴を実行器から削除したロボット同士の比較ではない。

初期計画は共通の青探索・180秒・帰還に固定し、訂正解釈だけに実Codex CLIを使う。
センサー履歴から「緑を見たが現在は見えておらず、青はまだ見ていない」機会を検出する。
その機会が90秒までに発生しなかった試行も記録し、別の配置へ差し替えない。
1件目を解釈した2シミュレーション秒後に、受理・質問のどちらでも同じ2件目を送る。
任意の質問へ適応的に答える人の対話成功率を測る実験ではない。

```bash
.venv-wsl/bin/python scripts/evaluate_corrections.py
```

実行前に `outputs/correction-evaluation-v1/frozen-inputs.json` へソース・仕様・依存バージョンを保存する。
各試行の観測、LLMへ渡した入力、生のJSON応答、速度指令、物理トレースを別ファイルに保存する。
結果は `evaluation.json` に逐次追記。429等の応答取得失敗でバッチを停止する。
プロセスが停止したことを確認し、外部条件が変わった後に同じコマンドで再開できる。
完了済み試行はスキップし、インフラ失敗の再試行は別ファイルで保存して前の失敗を残す。
凍結した内容が変わっていれば再開を拒否する。

安全に帰還しただけでは訂正後の任務成功に数えない。新しい緑の観測、青の明示的な取消し、
帰還完了、未達成タスクなし、元の期限・出発点の保持、待機中のゼロ速度指令まで要求する。
非発火・言語失敗・物理失敗・インフラ失敗を分けて報告する。
インフラ失敗後の停止位置を、モデルの言語能力や帰還能力の成績には使わない。

4配置・各1回に限るため、結果から一般的な汎化性能や統計的な優位性は主張しない。
同じ配置の結果を見て改良した場合、その配置は開発例へ移し、次の評価配置を新たに事前指定する。

## 初回の結果

2026-10-26、`ca0dbd5` に仕様とコードを固定した後、Ubuntu 24.04 / WSL2で全8試行を実行した。
LLMは `gpt-6-luna` / `xhigh` を要求し、MuJoCoと固定のGo2制御方策を使用した。
結果の途中で実装や配置を変更していない。観測履歴の比較以外の計画・実行コードも変更していない。

| 配置 | 訂正を入れる機会 | 履歴あり | 現在の観測のみ |
| --- | --- | --- | --- |
| 701 | なし（青を先に観測） | 通常の探索・帰還 | 通常の探索・帰還 |
| 702 | なし（青を先に観測） | 通常の探索・帰還 | 通常の探索・帰還 |
| 703 | あり | 再観測・青取消し・帰還を達成 | 質問2回、未達成を残して帰還 |
| 704 | なし（青を先に観測） | 通常の探索・帰還 | 通常の探索・帰還 |

訂正の機会は4配置中1配置。成功数は、その1組で履歴あり1/1、現在の観測のみ0/1。
非発火の6試行を、訂正成功や訂正失敗に数えていない。全8試行で安全に180秒以内に帰還し、
記録したトレースに障害物接触・転倒・非有限値はなかった。インフラ障害はなかった。

配置703では、両条件とも61.0秒の同じ位置・地図要約・残タスク・会話・期限で最初の入力を受けた。
LLMへ渡した内容は、過去の緑の観測2件を渡すか0件にするか以外、完全に一致した。
履歴ありでは72.2秒に `obs-60-green` を参照する再確認を追加し、青と帰還を保持した。
82.6秒に青だけを明示的な引用付きで取り消し、85.6秒に新しい緑の観測を取得。
104.8秒で帰還、帰還誤差0.1258 m、未達成タスクなし。

現在の観測だけの条件は「緑の観測記録がありません」と質問した。
次の入力でも参照先を得られず質問し、149.8秒で `not_found` として帰還した（誤差0.1175 m）。
帰還は完了したが、緑の再確認も青の取消しも適用されず、青を未達成として残した。
記録を捏造して成功にする動作はなかった。両条件とも質問・モデル待ち中はゼロ速度指令だった。

凍結した全ソースの指紋、8件の生ログのSHA-256、再採点、最初の入力の一致を再確認した。
仕様・環境バージョン・全試行の指標・訂正が入った試行のモデル入力と生の返答は
[correction-evaluation-validation.json](correction-evaluation-validation.json) に保存した。
再実行時に完了済み8件をスキップし、モデルの再問い合わせを行わないことも確認した。
Windowsの66テストが成功（物理9件スキップ）、新しい採点テスト3件はWSLでも成功。
ruffの検査・整形検査も成功した。物理単体テスト全体の再実行は行わず、凍結した実装を8回実MuJoCoで実行した。

この結果は、開発に使っていない1配置で履歴を使った訂正が成立した証拠にはなる。
ただし比較できたのが1組に限られ、一般的な汎化成功率や統計的な優位性は示さない。
人が質問に適応して回答する場合の比較でもない。次の評価では、事前に配置数を増やして機会の出現数を確保する必要がある。
