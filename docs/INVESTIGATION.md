# 冷蔵倉庫の能動的な設備異常調査

## 構成と情報の境界

`scripts/investigate.py` が調査専用の入口。既存の `src/main.py` と探索・訂正CLIは変更していない。
初期指示は「温度上昇の原因を調べ、証拠とともに報告して帰還」の1件だけでよい。

1. `docs/warehouse-manual.json` を一般知識として読み込む。電源盤と冷却機の給電関係、
   圧縮機停止の切分け、扉開放による熱流入、判断の限界を4節で定義した合成資料。
   実メーカーのマニュアルではなく、現在の設備状態や訪問順序を含まない。
2. `pai_motion.investigation.codex_investigation` が、指示・資料・設備位置の台帳・取得済み点検履歴・
   到達不能だった設備・残り時間・過去の判断だけをCodex CLIへ渡す。
3. Codexが3原因の仮説、根拠となる観測ID、参照資料ID、次の点検先と区別したい条件、
   または結論・根拠・不確実性を含む報告をJSONで返す。逐語的な思考過程は要求しない。
4. 検証器が設備ID、資料ID、観測ID、許可された行動、再訪禁止、仮説と結論の整合、
   最終診断の2設備以上の証拠を検査する。不正応答を固定の巡回計画へ置き換えない。
5. 移動器が既存の `ObservedMap` を使い、距離スキャンから0.1m格子地図を更新する。
   障害物膨張・Dijkstra経路・安全領域内の見通し追従・必要なfrontier探索は従来型アルゴリズムが担当。
   設備の台帳位置は既知だが、障害物の正解地図は経路計画に渡さない。
6. MuJoCo Go2が設備のサービス地点へ歩き、0.25m以内かつ並進速度0.05m/s以下・
   旋回速度0.08rad/s以下でのみ `InspectionWorld.inspect` が設備情報を返す。
   その観測が次のCodex入力に追加され、再び判断する。
7. 報告後は元の出発位置へ戻る。停止後の誤差0.15m以内と元の期限内を別々に確認する。

設備は電源盤 `supply`、冷却機 `cooler`、扉 `door` の3つ。シミュレータ内ではサービス地点の
床マーカーとして表示する。模擬の電圧・運転・温度・扉状態を返すもので、画像認識ではない。
一般資料のIDは `MAN-*`、現場観測のIDは `inspection-*` と分離する。
資料は小さいため全節を提示する。検索・埋め込み・外部DBは不要で、依存追加もない。

`investigation_world.py` だけが故障ラベルと未観測値を持つ。
同じ公開台帳から異なる故障を生成でき、プランナーへscene名、seed、正解原因を渡さない。
評価関数は任務終了後にだけ正解原因と証拠の十分性を照合する。
ログ全体には評価用の正解が含まれるが、LLMに渡った入力は各 `decisions[].context` に独立して保存する。

## 制限時間と失敗時の動作

標準の予算は360シミュレーション秒、指定可能範囲60〜600秒。点検先への移動は1件100秒まで。
帰還経路長を0.12m/sで移動する時間と15秒の余裕を確保し、最低20秒を帰還用に残す。
移動指令は前進最大0.25m/s、旋回最大0.6rad/s、0.2秒区間。
既存の50Hz歩行方策と500Hzの関節・物理制御をそのまま使う。

Codexは別スレッドで呼び出し、応答待ちはゼロ速度を指令して物理を進める。
推論待ち中は実時間0.2秒ごとにシミュレーションを0.2秒進める。実機の制御周期保証ではない。
CLIのタイムアウトは45秒。帰還余裕や応答期限に達した場合、不正出力、点検取得失敗では
実行器が原因未確定・調査未完了を報告して帰還を試みる。LLMが生成した報告と区別して記録する。
転倒・接触・地図上の安全経路喪失等の物理実行異常では停止し、危険な帰還を続けない。
帰還成功を保証するものではなく、`returned` と `within_deadline` を確認する必要がある。

## 実行

既存のREADMEのWSL2セットアップを完了した環境で、リポジトリルートから実行する。

```bash
.venv-wsl/bin/python scripts/investigate.py --scene A --headless --out-dir outputs/investigation-a
.venv-wsl/bin/python scripts/investigate.py --scene A --development-fault door_open --headless
.venv-wsl/bin/python scripts/investigate.py --scene A --development-fault cooler_fault --headless
# 固定済みの未見評価条件。再実行は追加試行であり、初回の未見評価とは区別する
.venv-wsl/bin/python scripts/investigate.py --scene B --seed 1102 --headless --out-dir outputs/investigation-b
```

`--prompt` で初期指示、`--seconds` で予算を指定できる。画面で確認する場合は `--headless` を外す。
開発用の故障上書きはMap Aだけで利用できる。出口コード0は正しい原因・十分な証拠・報告・期限内帰還の
全条件を満たした場合だけ。安全に帰還できても原因未確定なら終了コード1とする。

各JSONには入力、Codexの生JSONと検証済み判断、資料参照、観測、行動結果、距離スキャン、
0.1秒間隔の物理トレース、速度指令、失敗理由、評価専用状態、ソースのSHA-256を保存する。
`outputs/` は既存どおりGit対象外。解析に必要な生ログは削除しない。

```bash
# 成功ログの事後監査とコンパクトな集計
.venv-wsl/bin/python scripts/verify_investigation.py outputs/investigation-a/investigation-*.json \
  --output outputs/investigation-a/verified.json
# 通常テスト。物理を含める場合は既存と同じフラグを使う
PAI_SIM_TEST=1 .venv-wsl/bin/python -m unittest discover -s tests -v
```

監査は取得済み観測の完全な伝達、入力フィールドの分離、ID参照、点検距離・停止速度、
推論待ち中のゼロ速度、速度上限、接触・転倒、報告と帰還の順序、期限・位置誤差、証拠の十分性を検査する。
自由文の全主張を形式的に証明する検証器ではない。観測・資料と報告文の対応も確認する。

## 評価の扱い

Map Aは開発用。電源供給異常を既定とし、同じ配置で扉開放・冷却機故障にも切り替えられる。
Map Bは設備位置と障害物を変更し、故障も電源供給異常以外からシードで生成する。
Map Aでの調整後、Map Bを初めて生成する前に [investigation-evaluation.json](investigation-evaluation.json)
へソース25ファイルのSHA-256とシード1102・1試行・成功条件を固定した。
Map Bの正解・手順はプランナーに渡さず、Map Bを見てプロンプトやプログラムを調整しない。
単発の未見条件での成功は、一般的な汎化性能や他方式に対する優位性の証明にはならない。

## 実測結果（2026-11-02 JST）

Ubuntu 24.04 / WSL2、Python 3.12.12、MuJoCo 3.3.7、ONNX Runtime 1.23.2、Codex CLI 0.157.0。
CLIへ要求したモデルは既存と同じ `gpt-6-luna` / `xhigh`。サーバー側のモデル名は別途検証していない。
以下の4試行はすべて同じ凍結ソース・資料・プロンプトで実行し、事後監査を通過した。
時間は推論待ちと最終停止を含むシミュレーション秒。起動時の初期安定化は除く。

| 条件 | 実際の点検順 | 診断 | 時間 | 停止後の帰還誤差 |
| --- | --- | --- | --- | --- |
| Map A：電源供給異常 | 冷却機 → 電源盤 | 電源供給異常 | 88.4秒 | 12.9cm |
| Map A：扉開放 | 冷却機 → 扉 | 扉の長時間開放 | 92.2秒 | 12.0cm |
| Map A：冷却機故障 | 電源盤 → 冷却機 | 冷却機側の故障 | 100.4秒 | 11.4cm |
| Map B：seed 1102、初回 | 冷却機 → 扉 | 扉の長時間開放 | 92.6秒 | 12.3cm |

各試行とも、正解原因との一致だけでなく、診断に十分な2設備の現場証拠、報告後の帰還、
360秒以内、誤差15cm以内、接触・転倒なしを確認した。10Hzトレースの最小障害物余裕は12.7cm。
余裕は従来と同じ半径0.45mの機体近似による値で、実機の各リンクとの最短距離ではない。
Map B開始はソース固定の8.53秒後。全25ファイルと各実行ログのソースハッシュを照合している。

Map Aで冷却機を最初に点検した2条件を比べると、新しい観測によって次の行動が変わった。

- 0V・圧縮機停止：Codexは `MAN-POWER` と `MAN-COOLER`、`inspection-1` を参照し、電源盤へ。
  電源盤0V・遮断器トリップを追加観測し、供給異常を報告した。トリップ原因と冷却機の健全性は未確定とした。
- 230V・圧縮機運転・吹出−12°C：Codexは冷却運転が成立しているとして扉へ。
  開放900秒を観測し、資料の熱流入条件と照合して報告した。未点検の電源盤や複合要因の不確実性を残した。

固定順序で3設備を巡回する実装はない。LLMがどの設備から始めるかも固定しておらず、
冷却機故障の試行では電源盤を先に選んだ。原因ラベルだけを返す評価にはしていない。

失敗処理も確認した。最初の開発試行は、点検応答の `report` に中間報告文が入ったため拒否され、
原因未確定を報告して12.4秒で帰還した。その後、点検時に空文字を要求する条件をプロンプトにも明記した。
最終ソースの60秒予算試行では、遠い電源盤への移動中に帰還余裕へ達し、観測を捏造せず調査未完了を報告。
37.8秒、帰還誤差11.8cm、接触なしで終了し、成功とは数えず `incomplete`・終了コード1にした。

通常テストに加え、`PAI_SIM_TEST=1` の全105テストがスキップなしで成功した。
新規8件は点検条件、情報分離、出力検証、履歴を使う閉ループ、推論失敗時の帰還、
物理異常時の停止、到達不能を故障観測と扱わないこと、不十分な証拠の評価拒否を扱う。
新規PythonファイルのRuffと `git diff --check` も成功した。
実際の成功ログへ、未来の観測混入、資料IDを観測IDに偽装、遠距離点検、推論中の移動、
障害物接触の5種の改変を加える監査の自己検査も実施し、すべて拒否された。

小さな集計、判断と仮説の更新、観測値、最終報告、失敗記録は
[investigation-validation.json](investigation-validation.json) に保存した。
生ログはその `log` フィールドに記載した `outputs/investigation-*` 以下に残している。
途中の成功・失敗も上書きしていない。固定順序ベースラインとの比較は行っていない。

既存文書の不整合として、`third_party/NOTICE.md` にプロジェクト全体で地図と追加センサーを使わない
とあったが、既存の探索実装はすでに両方を使っていた。今回、制御器の移植範囲と上位層の追加機能を
区別する記述へ修正した。

温度値や設備状態は合成値で、熱伝導・電気回路・故障進行の物理モデルではない。
自己位置はMuJoCo真値、距離センサーは理想化されている。カメラ認識・SLAM・実機・複合故障・
動的故障・修理行動は対象外。同じ設備は静的な1回点検とし、時系列の再点検には対応しない。
既存の凍結済み探索・訂正評価は変更せず、今回の開発結果とも統合しない。
