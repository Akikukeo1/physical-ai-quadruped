# Luna 6 / xhigh の最初の言語実験

2026-10-26、`b9229bb` で固定した `gpt-6-luna` / `xhigh` を使用した。
呼び出しで指定した設定であり、サーバー側の実モデル名を別途取得した記録はない。
過去のモデル未指定の結果は変更しない。

```bash
.venv-wsl/bin/python scripts/probe_corrections.py \
  outputs/task-revision-dev/reobserve/plan-20261024T201811354659Z.json \
  --out-dir outputs/language-probes-luna6-xhigh
```

保存済みの同じ観測を使い、8入力 × 履歴あり／なしの16条件を予定した。
このバッチは言語解釈だけで、ロボットを動かした試行ではない。
事前の期待値は既存スクリプトのまま。結果に合わせて変更していない。
入力・応答・検証結果・元ログのSHA-256は [luna6-language-validation.json](luna6-language-validation.json)。

| 履歴ありの入力 | 応答 | 事前期待との一致 |
| --- | --- | --- |
| 青をやめて緑へ変更 | 青を取消し、緑を探索して帰還 | 一致 |
| 青を保持して緑を先に追加 | 緑 → 青 → 帰還 | 一致 |
| 緑をもう一度確認して青を再開 | 過去の緑の観測2件のどちらかを質問 | 不一致 |
| さっき見えた対象をもう一度確認 | 緑を再確認 → 青 → 帰還 | 一致 |
| 青を取消して今すぐ帰還 | 青を取消して帰還 | 一致 |
| あっちを先にして | HTTP 429、応答なし | 採点対象外 |

応答を得た5件中4件が期待したタスク列と一致した。1件は安全な確認質問だったが、
再確認へ進むという期待を満たさなかった。スキーマや実行側の検証で弾かれた応答ではない。
同じ色の過去の観測が複数ある場合に、どの記録を使うかという余分な曖昧さが残っている。
この結果を受けてプロンプトや採点基準を変更する場合、同じ条件での再試行は開発実験と明記する。

6件目で429となり、その時点で停止・保存した。残り10条件は未実施。
これは4/16というモデル正解率を意味しない。履歴なし条件は未実施であり、履歴の効果も比較できない。
過去の16/16はモデル・確認方針が異なるため、今回の4/5とモデル間の優劣比較には使えない。

## 次に確かめること

1. レート制限解消後、短い回答による確認解決と帰還をLuna指定の実MuJoCoで検証する。
2. 開発条件で、対象が1個でも観測が複数あるときの選択方針を明文化する。既存の履歴を消して解決しない。
3. 方針を固定してから、新しい配置・言い回しの比較条件を事前に決めて実行する。
   訂正適用・元の義務の保持・新規観測・期限内帰還を別々に採点し、
   確認回数・停止時間・物理失敗・インフラ失敗も分ける。

現時点でLuna指定の対話付きロボット完遂、未知配置への汎化、他手法への優位性は未検証。

## 未完了条件だけの実行

実験スクリプトに `--case` と `--condition` を追加した。既定では従来と同じ16条件を実施する。
429等の応答取得失敗は `ERROR` と表示し、意味解釈の不一致である `FAIL` と分ける。
問い合わせを得た条件を再実行するときは、初回を上書きせず新しい試行として残す。
モデル・推論強度・選択条件・計画生成ソースのSHA-256も結果へ保存する。
通常のロボット実行ログにも `requested_codex_settings` を保存する。サーバー側モデルの証明ではなく、
アプリからCLIへ要求した設定の記録である。

```bash
.venv-wsl/bin/python scripts/probe_corrections.py \
  outputs/task-revision-dev/reobserve/plan-20261024T201811354659Z.json \
  --out-dir outputs/language-probes-luna6-remaining \
  --condition history --case ambiguous negation unsupported
```

## 同じ指示文での追加試行

`cc1a0e9` で、未完了の履歴あり3条件はすべて期待どおりだった。初回の5応答と合わせて7/8が一致。
履歴なしは最初の5条件すべて一致した。再確認2条件は過去の観測がないため `clarify` を返し、
観測IDを捏造しなかった。6条件目の曖昧入力で再び429となり停止。履歴なしの残り3条件は未完了。
生の応答と検証結果を [luna6-followup-validation.json](luna6-followup-validation.json) に保存した。

同じコミットの実MuJoCoで `examples/dialogue-short-answer.json` を試した。
「緑です。」の後も `obs-22-green` と `obs-47-green` のどちらかを質問し、
次の青取消し入力でも同じ質問を繰り返した。全3入力が `clarify` で、緑の再確認も青の取消しも実行されなかった。
152.0秒で `not_found` として帰還、帰還誤差0.1134 m。接触・転倒はなく、待機中の指令もゼロだった。
処理の `status=completed` は帰還を終えた意味で、**訂正された任務を達成した成功例ではない**。
青の未達成タスクと3件の質問をログに残した。

この失敗から、単一対象を何度も観測した記録の選び方を明文化する必要があると分かった。
以下の変更・再試行は、この既知の開発例への修正として扱い、新しい汎化評価には数えない。
