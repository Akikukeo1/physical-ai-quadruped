# フィールドエリアの通行条件

`tools/area-editor.html` をブラウザーで開き、フィールド上をドラッグして最大8個の長方形を配置し、
「JSONを保存」で出力する。座標枠と出発地点のみを表示し、障害物と対象の位置は表示しない。
最初のエリアは `area1`、次は `area2` と命名される。保存先はブラウザーのダウンロード設定に従う。
描き直す場合は最後から削除する。既存JSONの読込や多角形の描画は未対応。

生成されたJSONをWSLから参照できる場所に置き、以下の `--field-areas` をそのパスに変更する。
次は同梱の2エリアと指示を使う再現例。ビューアを表示しながら録画する場合は `--headless` を外す。

```bash
MUJOCO_GL=egl bash scripts/demo.sh --task search --planner codex --seed 305 --headless \
  --field-areas examples/field-areas.json --correction-script examples/field-dialogue.json \
  --video outputs/field-areas.mp4 --out-dir outputs/field-areas
```

実行中に指示を出すには `--correction-script` を `--correction-file outputs/correction.txt` に替え、
READMEのライブ入力手順を使う。通常のエリアモードではCodexの応答は通行条件の変更だけを扱い、
探索対象やタスク順の変更、必須通過は扱わない。不明なエリアなどは確認するようモデルに指示する。
タスク訂正とエリア変更を統合した実験モードは [AGENT_SEARCH.md](AGENT_SEARCH.md) を参照。
実行開始時は全エリアが通行可能で、指定されなかったエリアの条件は維持する。
「通っていい」は通行の許可であり、必ず通ることを意味しない。
Codexが通行条件を解釈し、既存の観測地図と探索アルゴリズムが実際の経路を選ぶ。

MuJoCoでは通行可能を水色、禁止を赤色で表示する。領域内の数字はJSON配列での順序であり、
起動時に `1=area1` のような対応を表示する。矩形の可視化は衝突や距離・色センサーを遮らない。
禁止の判定対象はロボットの中心で、計画時に15 cmの余裕を取り、5 cm以内では停止する。
範囲の有効化で現在位置や観測済み帰還経路が安全でなくなる場合、状態を変更せず確認する。
これは離散時間・シミュレータ真値を前提とした判定で、機体全体や実機での安全保証ではない。

## 開発用実行

seed 305で実Codex CLI（要求モデル gpt-6-luna、xhigh）とMuJoCoを1回実行した。
「エリア2を通らないで」→「エリア1は通っていいけど、エリア2は引き続き避けて」→
「エリア2も通っていいよ」の順に受理され、禁止状態は `[area2]` → `[area2]` → `[]` と変化した。
青を発見して80.0秒で帰還し、帰還誤差は約0.096mだった。
最初の試行はモデルの出力した引用が検証に通らず停止したため、引用方法のプロンプトを調整して再試行した。
これは開発ケースであり、条件の意味解釈は引用の検証だけでは保証されない。
別の実Codex呼び出しでは、両エリアが通行可能な文脈で「エリア1は通るが、エリア2は通るな」から
`area1=allow` と `area2=avoid` を返した。これは言語解釈のみの確認で、物理走行はしていない。

禁止有効中の0.1秒間隔の物理トレースではエリア2との最短距離は約1.154mだった。
この試行はエリアの近くでの迂回や、未知の指示・配置への汎化を実証するものではない。
実行ログと録画は `outputs/field-area-dev-2/` と `outputs/field-area-dev-2.mp4` に保存しており、Git管理対象外。

円制約の削除後、同じ開発ケースを実Codex CLIとMuJoCoで再実行し、
禁止状態 `[area2]` → `[area2]` → `[]`、青の発見と99.2秒での帰還を確認した。
帰還誤差は約0.111m。ログは `outputs/field-after-circle-removal/` に保存している。
