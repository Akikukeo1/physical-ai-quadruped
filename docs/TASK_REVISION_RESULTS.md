# 観測履歴に基づくタスク訂正

以下は単発訂正時点の記録。現行の[複数回の訂正と確認対話](DIALOGUE_RESULTS.md)では、確認用の `question` フィールドと `clarify` 状態を追加した。ここに保存した過去のログは変更しない。

色変更だけのMVPから、実行中の目的と順序を組み替える入口へ拡張した。
作業前チェックポイントは `1def0a6`。Python・uv・MuJoCo・歩行方策は既存の版を使い、依存関係は追加していない。
既存の探索・帰還処理を使い、LLMが出すものは実行可能なタスク列に限定する。

## 今回扱える指示

- 「青ではなく緑に変更して」：青を取り消し、緑の探索を追加する。
- 「緑も先に探して、それから元の青の探索を続けて」：緑の探索を挿入し、青を保持する。
- 「さっき見た緑をもう一度確認してから、青の探索を続けて」：過去の観測を参照する再確認を挿入する。
- 「青の探索は中止して、今すぐ出発地点へ戻って」：取消しを記録して帰還する。

未達成タスクの並べ替えも同じプロトコルで扱う。
LLMが決めるのはタスクの組合せ、順序、取消し、どの観測を参照するか。
格子地図上の経路、探索点の選択、歩行、衝突判定はPythonと既存の制御器が担う。
初期の検索指示のJSONは従来の単一色＋制限時間のままで、複数タスクへの拡張は今回の訂正入力で行う。

## LLMへ渡す情報

訂正を受信した時点の切り離したスナップショットを渡し、同じ内容をログへ保存する。
モデル待ち中も観測は続けるが、LLMへ渡した履歴を後から書き換えない。

- 現在のタスク、未達成タスクとID、完了済みタスク。
- ロボットの位置・向き、元の出発地点・締切・残り時間。
- 各色の最初と最後の観測。観測ID、色、時刻、**観測時のロボット位置**、距離。
- 最新スキャンの時刻と見えた色、距離センサーの上限。
- 観測地図の解像度・自由／占有セル数、訪問済み探索点。

対象の隠れた座標、シード、正解の障害物配置、未知領域の地図は渡さない。
観測は距離・最初に当たった表面の色であり、画像認識ではない。自己位置は正解値を使う。
LLMへ送る観測履歴は各色の最初と最後を選んだ要約で、全スキャン列ではない。

## 訂正JSON

例：「緑を再確認してから元の青探索を再開する」。観測IDは実際に渡されたものだけを使う。

```json
{
  "intent": "緑を再観測してから青の探索と帰還を続ける",
  "status": "accept",
  "steps": [
    {"id": "reobserve-green-1", "action": "reobserve", "target": "green", "observation_id": "obs-47-green"},
    {"id": "search-1", "action": "search", "target": "blue", "observation_id": null},
    {"id": "home", "action": "return_home", "target": null, "observation_id": null}
  ],
  "cancelled": []
}
```

`search` は探索して観測すれば完了し、過去の検出でも条件を満たす。
`reobserve` は参照先と同じ色について、**そのタスク開始後の新しいスキャン**で2本以上のレイを得る必要がある。
必要なら、参照した観測時のロボット位置へ、観測済みの安全な地図内で移動する。
途中で再検出できれば完了するため、古い位置への到達や対象への接触は必須ではない。
古い位置からも見えない場合は、確認済みと扱わず失敗として停止する。

タスクは最大8件、IDは最大40文字。未取消しのタスクは同じIDと内容で残す。
取消しには `{"id":"search-1","instruction":"青の探索は中止"}` のように、入力文からの正確な引用を付ける。
帰還は元の `home` を最後に1回だけ保持し、締切は延長しない。
引用の一致は意味解釈の正しさを保証しない。LLMが取消しの意図を取り違える可能性は、今後の比較実験で評価する。

存在しない観測ID、色の違う参照、元タスクの黙った削除・IDの使い回し、座標・コード・余分なフィールドを拒否する。
初期探索JSONとCLI引数は変更していないが、訂正JSONはMVPから変更した。
Pythonの訂正コールバックは `correction_planner(prompt, plan, context)` を受け取る。
旧形式の訂正JSONを現行コードへそのまま入力することはできない。過去のログは当時の形式として保持する。

## 実行とログ

```bash
bash scripts/demo.sh --task search --planner codex --seed 305 --correct-at 55 --correction '青の探索は続けて。ただし、さっき見た緑をもう一度確認してからにして。最後は戻ってきて' --headless
```

ライブ入力には従来どおり `--correction-file` を使う。
訂正は帰還開始前の1回。待機中はゼロ速度の下で物理と観測を進め、停止確認後にタスク列を採用する。
観測地図・訪問履歴・最初の検出は捨てない。元の締切が待機中に尽きた場合は失敗となる。

`corrections[].context` にLLMへ渡した状態、`correction` に採用したタスク列を保存する。
`decisions` はタスク開始・完了・根拠の観測を記録する。
`result.tasks` は `pending / completed / cancelled` を分けて保存する。
`found` は全タスクの証明ではない。全体の `outcome` と残りタスクも確認する。
未達成のまま帰還余裕を使い切りそうなら `not_found` として帰還し、未達成タスクを残す。
探索を明示的に取り消して帰った場合は `returned` であり、発見成功とは区別する。

## 検証の範囲

実行記録の集計は [task-revision-validation.json](task-revision-validation.json)。
配置と言い回しは開発用であり、未見の配置・言い回しへの汎化を示すベンチマークではない。
モックを使う境界検査と、実Codexを呼ぶ試行、実MuJoCoの物理テストを区別する。

2026-10-25、Ubuntu 24.04 / WSL2で、初期計画・訂正解釈とも実Codexを使って次の4件を実行した。

| 訂正 | シード | 実際の動作 | 探索開始から停止まで | 帰還誤差 |
| --- | --- | --- | --- | --- |
| 緑を再確認してから青を継続 | 305 | 74.4秒に緑を再観測、117.4秒に青を発見して帰還 | 137.4秒 | 11.9 cm |
| 青を中止して今すぐ帰還 | 0 | 青の取消しを記録し、発見済みとは扱わず帰還 | 27.6秒 | 12.0 cm |
| 緑の探索を先に追加 | 0 | 緑を探索し、保持した青の依頼を完了して帰還 | 87.2秒 | 12.3 cm |
| 青を緑に置き換え | 305 | 青の取消しを記録し、22.0秒の緑の履歴を使って帰還 | 74.0秒 | 9.8 cm |

対象の検出・訂正時刻はMuJoCoの物理時刻で、初期安定化1秒を含む。
所要時間は探索開始からで、最後の停止2秒を含む。実時間性能の保証ではない。

再確認の試行では、56.0秒の受信時点で緑は視界外だった。
LLMは渡された22.0秒と47.0秒の観測から、47.0秒の `obs-47-green` を参照先に選んだ。
62.4秒に訂正を適用し、74.4秒の新しい観測を得るまで再確認を完了にしなかった。
青の `search-1` は取り消されず、その後に探索を再開した。元の地図・検出履歴・締切を保持し、接触なく帰還した。

探索追加の試行では、緑の探索中の15.4秒に青もセンサーへ映っていた。
緑を68.4秒に発見した後、69.4秒にその青の履歴を使って依頼を完了した。
タスクの順序は実行・完了の順序であり、360度センサーに別色が偶然映る順番までは制限しない。
後から新しい観測を要求する場合は `reobserve` を使う。

4件とも180秒制限・元の帰還条件を保持し、待機中の全指令がゼロ速度、接触・転倒なしで完了した。
これは4件の開発試行の結果であり、一般的な自然言語理解の成功率を示す値ではない。
