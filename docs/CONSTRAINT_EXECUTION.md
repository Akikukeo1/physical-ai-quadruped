# 観測地点を基準にした制約付き訂正

試作した制約付き経路と、観測IDに基づく訂正JSONを実験的に接続した。
対象は、探索途中に入力する「過去にロボットが観測した地点の周囲へ、ロボットの中心を入れない」制約。
対象物の位置や機体全体が領域外であることを保証するものではない。
初期の探索指示には制約を含められず、観測後の訂正として入力する。

```bash
bash scripts/demo.sh --task search --planner codex --seed 305 --headless \
  --constraint-revisions --correction-script examples/constraint-dialogue.json \
  --out-dir outputs/constraint-dialogue-dev
```

この指定を使うにはCodexと訂正入力が必要。従来の訂正モードも使える。
LLMは既存のタスクと制約を受け取り、観測ID・半径・発言の引用を持つJSONを返す。
検証器は根拠となる観測の存在、半径、タスクと制約の保持、引用付きの解除を検査する。
引用があることは発言の意味を正しく解釈した証明ではない。

制約を適用する前に、停止後の現在地と観測済み地図上の帰還経路、残る再確認の目標地点を調べる。
この方式で到達できなければ、提案を適用せず現在の状態を維持し、確認質問に切り替える。
質問がLLMによるものか、実行器の到達可能性検査によるものかはログに残る。
禁止領域がある間は、探索と帰還も制約を避けた格子経路を使う。
計画時は円の外側15 cmを余裕として確保し、0.2秒ごとの姿勢観測で円に5 cmまで近づけば停止する。
それらの値はこのシミュレータでの保守的な設定で、連続的な安全保証や実機での保証ではない。

模擬運動の単体テストでは、制約追加、実行器による到達不能な再確認への質問、解除、残タスクの完了と、
現在地や帰還を塞ぐ制約を適用しないことを確認した。これらのテストは物理シミュレーションではない。
## 開発試行の結果

`9061cb1` を固定し、seed 305で実際のLuna + MuJoCoを2回試した。
いずれも緑の観測地点を中心とした半径0.5 mの制約を追加し、同じ地点に戻る要求に質問し、
明示的な解除後に新しい緑の観測を取得した。質問は両方ともLLMが生成した。
元の期限・出発地点を保持し、モデル・回答待ち中はゼロ速度を指令した。

| 元の予算 | 結果 | 実行順 | 帰還誤差 |
| --- | --- | --- | ---: |
| 180秒 | 159.0秒で未発見として帰還。青は未達成 | 緑再確認 → 帰還 | 0.1251 m |
| 240秒 | 173.8秒で青・緑を確認して帰還 | 青探索 → 緑再確認 → 帰還 | 0.1020 m |

240秒の試行は180秒試行の未達成を見て予算を変更した開発試行で、独立した評価ではない。
当初の目標は緑を再確認してから青を探索する順序だったが、入力文にその順序を明示できていなかった。
実際の240秒試行では青が先になったため、当初の順序どおりに動いたとは言えない。
また240秒試行でLLMは「別の場所から確認」という選択肢も質問したが、
現在の再確認器は代替観測位置を計画できない。この提案は未対応である。

制約が有効な間のロボット中心と観測地点の距離は、記録された0.1秒間隔の位置で最小1.24 mと1.25 mだった。
有効期間中の非ゼロ速度指令はそれぞれ6回、23回。対象半径0.5 mより外側にいたが、
禁止領域の近くを迂回する動作はこの2試行では示せていない。記録された物理トレースに障害物接触・転倒はなかった。
生ログ参照、SHA-256、状態と計測値は [constraint-execution-validation-initial.json](constraint-execution-validation-initial.json)。

Windowsの80テストは成功（物理9件スキップ）。制約付き実行の4テストは模擬運動であり、
上記2試行は実MuJoCoの開発試行。未知配置での一般性や条件の意味解釈の正確さはまだ示していない。
