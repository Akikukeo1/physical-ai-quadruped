# 運動学的プローブによる能動計測

既存の設備調査に `--probe` を追加した。別タスクや別の歩行方策は作っていない。
プローブを使わない既存の3原因の設備調査、資料、スキーマ、凍結評価JSONは保持している。

## 機構と歩行との分離

プローブは長さ0.22mの1自由度の運動学的な首振りモデル。
取付位置はGo2基準で前方0.1m・上方0.17m、角度範囲は±1.1rad、速度上限は0.6rad/s。
先端の位置と方向は、現在のGo2の自由基底の位置・クォータニオンとプローブ角度から計算する。
表示には[MuJoCo 3.3.7のmocap body](https://mujoco.readthedocs.io/en/3.3.7/XMLreference.html#body)を使い、
ロボットの力学ツリーとは独立した、衝突しない表示体として追従させる。
Go2の `qpos` を動かしてロボットを運ぶ処理や、機体の固定は使っていない。

脚の12関節・12アクチュエータ、ONNXの225次元入力・12次元出力、各部品の質量・慣性は変更しない。
モデルの `nq=19, nv=18, nu=12` の検査も維持している。
表示体の慣性はロボットへ接続せず、計測器の実際の荷重や反力を模擬しない。
**物理アームの力学制御や、ペイロード付き歩行の実証ではない。**

歩行中は0radの格納姿勢を保持する。格納は前方へ沿わせる姿勢で、伸縮機構ではない。
先端までの水平包絡は既存のロボット安全半径0.45m以内。
展開中の前進・旋回指令は拒否する。首振り開始時にも並進・旋回速度を確認し、ゼロ速度指令の下で動かす。
MuJoCoの物理と歩行制御は計測中も進む。

## 計測モデルと物理的な条件

対象は冷却機の2つの模擬計測アクセス領域。
温度用採気領域と風速用測定領域を吹出口の左右に設け、必要なロボット位置と首振り角が異なる。
これらは簡易設備の校正済みサービス位置という設定で、汎用のセンサー設置最適化ではない。
吹出口の円盤と2つの色付き領域も表示する。全設備の3D化は行っていない。

測定行動は既存の観測地図で指定領域へ移動し、機体を所定の向きへ旋回、静止、実際の現在姿勢から
必要なプローブ角を計算して展開する。計測後は格納してから次へ進む。
LLMは測定項目を選び、幾何計算・位置合わせ・角度制限は実行器が担当する。

値を取得できる条件は次のすべて。

- 先端と吹出口の距離が0.15〜0.42m。
- 先端の方向と吹出口方向の誤差が16度以内。
- 吹出口より西側で、高さの差が0.07m以内。
- 温度用は吹出口に対するy差が−0.30〜−0.04m、風速用は+0.04〜+0.30m。
- プローブを展開し、角速度0.08rad/s未満。
- 機体の並進速度0.05m/s以下、旋回速度0.08rad/s以下。
- 先端から吹出口までMuJoCoのレイキャストで環境障害物による遮蔽がない。

不成立なら `valid=false, value=null`。ゼロや過去の値を返さず、診断の証拠として参照することも拒否する。
測定対象IDだけでは値を得られず、現在の先端幾何が必須になる。
計測領域と吹出口位置は既知のサービス台帳として公開し、未観測の温度・風速や原因は公開しない。

空気場は単純な解析式。吹出口からの軸方向距離を `d`、中心軸からの距離を `r` とすると、
減衰係数 `g = exp(-0.4*d) * exp(-(r/0.5)^2)` を使う。
局所温度は `8 + (吹出口温度 - 8)*g`、局所風速は `吹出口風速*g`。
温度は周囲空気との混合、風速は吹出口からの減衰を簡略化したもので、CFD・熱伝導・センサー誤差の
物理シミュレーションではない。源の温度・風速はシミュレータ専用状態から設定する。
プローブが対象に接触する力や衝突、赤外線放射は模擬していない。

## 資料と診断ループ

`warehouse-probe-manual.json` は合成の一般技術資料で、現在の正解は含まない。
従来の資料と区別し、冷却・送風・扉の関係を記載している。
冷却機の通常点検は電圧・冷却要求・圧縮機の運転表示だけを返す。
`supply_air_c` はプローブ使用時には通常点検から除き、温度の取得を迂回できないようにした。

Codexは従来の `inspect/report` に加え、`measure(cooler, air_temperature/airflow)` を選べる。
JSONには測定目的、期待する区別、資料ID、観測ID、仮説の状態、結論・不確実性を保存する。
位置や角度、速度、コードをLLMに生成させていない。
無効な測定、未知の項目、同じ項目の再測定、架空の資料・観測IDは拒否する。
同一設備の異なる測定チャネルは独立した証拠として扱う。

原因候補はプローブ使用時だけ送風不足を加えた4種類。

| 設備状態・測定の組合せ | 支持する原因 |
| --- | --- |
| 電源盤と冷却機入力が0V | 電源供給異常 |
| 正常給電、暖かい吹出空気、正常風速 | 冷却系故障 |
| 正常給電、氷点下の吹出空気、極小風速 | 送風不足 |
| 氷点下の空気、正常風速、長時間の扉開放 | 扉開放 |

冷却系故障・送風不足・扉開放の3条件は、通常の冷却機点検では同じ表示になる。
運転表示だけから原因を判定せず、温度・風速の新しい測定が必要になる。
送風不足でファン故障か風路閉塞かまでは判別できない。
これらの十分性判定は評価器の処理で、正解ラベルとともに任務終了後に使用する。
LLM入力には一般資料と取得済み観測だけが入る。

## 実行と検証

既存のWSL2セットアップ後、リポジトリルートで実行する。

```bash
.venv-wsl/bin/python scripts/investigate.py --scene A --probe --development-fault airflow_fault \
  --headless --out-dir outputs/probe-airflow
.venv-wsl/bin/python scripts/investigate.py --scene A --probe --development-fault cooler_fault \
  --headless --out-dir outputs/probe-cooling
.venv-wsl/bin/python scripts/investigate.py --scene A --probe --development-fault door_open \
  --headless --out-dir outputs/probe-door
# --probeなしの従来の設備調査も利用可能
.venv-wsl/bin/python scripts/investigate.py --scene A --headless

PAI_SIM_TEST=1 .venv-wsl/bin/python -m unittest discover -s tests -v
.venv-wsl/bin/python scripts/verify_investigation.py outputs/probe-airflow/investigation-*.json \
  --output outputs/probe-airflow/verified.json
```

生ログは10Hzの機体・先端姿勢履歴、速度指令、測定前・展開・格納姿勢、測定の距離・方向・遮蔽判定、
値、LLMの全入力と出力、仮説更新、帰還・評価、ソースSHA-256を含む。
監査器もプローブ使用を識別し、各測定の幾何と値の再計算、展開中の歩行禁止、格納後の移動、
未観測情報の分離、報告・帰還・証拠の十分性を検査する。
自由文の全主張を形式的に証明するものではない。

今回の試行はすべて開発検証。過去のMap Bの未見評価を新実装の成績には流用していない。
CLIでも `--probe --scene B` は受け付けない。
過去の `investigation-evaluation.json`、`investigation-validation.json`、従来の資料・スキーマと生ログは保持する。

## 実行結果（2026-11-02 JST）

実Codex CLIと自由に接地したMuJoCo Go2で、次の任務が成功した。
既存と同じ `gpt-6-luna` / `xhigh` を要求し、CLIタイムアウトは45秒のまま。
モデルのサーバー側実体を別途確認したという意味ではない。

| 条件 | 空気温度 | 風速 | 診断 | 任務時間 | 帰還誤差 |
| --- | --- | --- | --- | --- | --- |
| プローブ・送風不足 | −8.790°C | 0.043m/s | 送風不足 | 140.8秒 | 10.0cm |
| プローブ・冷却系故障 | 8.000°C | 1.753m/s | 冷却系故障 | 184.6秒 | 12.7cm |
| プローブ・扉開放 | −8.489°C | 1.786m/s | 扉開放900秒 | 124.8秒 | 11.9cm |
| 従来モード・電源異常 | プローブ未使用 | プローブ未使用 | 電源供給異常 | 94.6秒 | 12.9cm |

時間は初期安定化を除き、推論待ち・位置合わせ・計測・格納・最終停止を含むシミュレーション秒。
4試行とも360秒の期限内に証拠付き報告と帰還を完了し、接触・転倒なし。
10Hzトレースの最小障害物余裕は12.8cm。従来と同じ半径0.45mの機体近似による値。
監査器で全4ログの観測伝達、先端幾何、静止条件、展開・格納、速度上限、診断の十分性を確認した。
実行時に保存したソースのハッシュも、検証時のソースと一致した。

LLMは全3プローブ試行で、資料と点検履歴から温度を選び、その観測を受けて風速を選んだ。
順序をプログラムで固定していないが、この3試行では温度→風速という同じ順になった。
送風不足では氷点下と低風速の組合せからその場で報告した。
扉開放では氷点下と正常風速から扉点検へ進み、900秒の開放を追加観測して報告した。
冷却系故障では暖かい空気と正常風速から冷却不成立を支持し、扉の閉鎖も確認した。
**計測値による仮説・診断と次の行動の変化は確認したが、測定順序の多様性やLLMの他方式に対する優位性は示していない。**

新規6テストを含む全111テストが `PAI_SIM_TEST=1` でスキップなしに成功した。
プローブ有無で全ロボット部品の質量・慣性が一致し、同じ前進・後退・左右旋回後の `qpos` が
絶対誤差1e-10以内で一致することも検査した。格納時の歩行・停止、展開中の歩行拒否、
適切な両計測位置への移動・計測・格納・帰還を、機体を固定せずに検査した。
距離・方向・高さ・アクセス領域・遮蔽・プローブ運動・格納による無効化、値の非公開、
資料とスキーマのID一致、不正測定項目・無効証拠の拒否も確認した。
RuffとWindows改行を考慮した `git diff --check` は成功している。

最初の開発試行はCodexが資料IDを重複して返したため拒否され、原因未確定を報告して帰還した。
調査中に新しい資料IDが出力スキーマに不足していたことも発見し、IDの許可集合と重複禁止の指示を修正した。
拒否された応答を自動補正して採用する処理は追加していない。失敗ログも保持している。

小さな集計と測定・仮説・報告は [probe-validation.json](probe-validation.json)。
詳細ログは各 `results[].log` の `outputs/probe-*` 以下。
実際のMuJoCo表示の格納・展開静止画と状態履歴は `outputs/probe-geometry/` に保存し、
温度用・風速用の展開画像を確認した。動画・演出素材は作成していない。

赤外線表面温度は検討したが、今回の原因候補は温度・風速・既存点検で区別できる。
独立した診断価値のない測定項目の追加を避け、未実装とした。
現状は固定設備・静的な故障・既知サービス台帳・理想的な距離センサー・真値オドメトリに限定する。
任意の設備形状や設置誤差、カメラ認識、実機、プローブの物理関節・荷重・接触力は未検証。
