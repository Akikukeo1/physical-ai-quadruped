# 訂正文の言い換えと観測履歴の比較

優秀賞に向けた追加機能の前に、現在の訂正解釈が対応できる範囲を確認する開発実験。
作業前チェックポイントは `00da47e`。ロボットの制御コードやモデルへの指示文は変更していない。
既存の実MuJoCo試行の56秒時点の状態を固定し、実際のCodex CLIへ16回問い合わせる。
新たなロボット実行は含まず、言語解釈と出力検証の結果を測る。

## 条件

同じ8入力を、観測履歴あり／なしの2条件で試す。
履歴ありには緑の22秒・47秒の観測があり、現在は青も緑も視界外。
履歴なしでは `context.observations` だけを空にし、現在位置、残タスク、締切、最新の可視色、地図要約を同一にする。

| 入力の種類 | 期待する結果 |
| --- | --- |
| 青をやめて緑に変更 | 青の取消しと緑の追加、帰還 |
| 青をやめずに緑を先に追加 | 緑 → 元の青 → 帰還、取消しなし |
| 緑をもう一度確認して青を再開 | 履歴ありは再確認 → 青 → 帰還、履歴なしは拒否 |
| さっき見えた対象をもう一度確認 | 履歴ありは唯一観測された緑を参照、履歴なしは拒否 |
| 青を取り消して今すぐ帰還 | 青の取消しと帰還 |
| あっちを先にして | 曖昧な対象を推測せず拒否 |
| 緑に変更しないで青を続ける | 青と帰還を保持 |
| 帰還不要・時間制限なし | 現行で変更できない条件として拒否 |

期待するタスク列・取消しIDは問い合わせ前にスクリプトへ固定し、生の返答と一緒に記録する。
受理の場合は実際の実行側の検証を通ること、動作・対象・取消しIDが一致することを確認する。
拒否の場合はモデル自身が `status=reject` を返したかを確認する。
検証で弾かれただけの不正な受理計画、モデルのタイムアウトは正解に数えない。

## 再現

```bash
.venv-wsl/bin/python scripts/probe_corrections.py outputs/task-revision-dev/reobserve/plan-20261024T201811354659Z.json
```

`outputs/language-probes/` に時刻付きJSONを作り、各応答の後に結果を保存する。
同じファイル名の上書きや既存の探索ベンチマークの変更はしない。
スナップショットのSHA-256と入力・期待値、生の応答、検証エラーを含む。
Codex CLIのモデル設定は既存の実装どおり標準設定を使うので、将来同じ返答になる保証はない。

## 今回の結果

2026-10-25、実Codex CLIで16条件を実施し、16/16が事前の期待結果と一致した。
生の応答と検証結果は [language-probe-validation.json](language-probe-validation.json)。
履歴ありは受理6件・拒否2件、履歴なしは受理4件・拒否4件だった。
「もう一度」「さっき見えた対象」の2入力は、履歴ありでは47秒の `obs-47-green` を参照し、
履歴なしでは過去の記録がないことを理由に拒否した。
曖昧な「あっち」と帰還・期限の取消しは両条件で拒否し、否定表現では青のタスクを保持した。
タイムアウト・不正な受理計画・意図と異なる取消しはこの16件にはなかった。

現行の実行器は拒否を受けると失敗として停止する。返答JSONに元の手順が残っていても、実行を継続したことは意味しない。
スクリプトの採点処理は自己検査を実施し、ruffの静的検査・整形検査も成功。
制御コードは変更していないので、物理テスト全体は再実行していない。

## 解釈の限界と次の実験

各入力は各条件で1回。単一の既知の配置と状態に基づく開発用の言語実験であり、汎化性能や完遂率は測っていない。
履歴のない条件では再確認の期待値を拒否としているため、単純な正解数だけで履歴の優位性を主張しない。
一方、履歴によって参照を解決し実行可能な計画を作れるかは比較できる。

曖昧な入力を拒否できても、人に確認して任務を続ける機能はまだない。
次は複数回の訂正と確認応答を扱い、最初の依頼・途中の変更・観測履歴・元の締切を引き継げるかを実MuJoCoで試す。
